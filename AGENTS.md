# SpriteStudioPlayer for Unity — AI Agent Guide

## Operating rules

*   Keep changes scoped to the requested task.
*   Do not commit, push, or open PRs unless the user explicitly asks.
*   Before editing, read enough surrounding context to understand callers and invariants.
*   Follow the existing code style of the file you touch (naming, C# conventions).
*   **Dependencies:** only standard Unity packages (Burst, Mathematics, Collections, Timeline). Do not add third-party packages.
*   **SDK alignment:** when changing core playback, check `SpriteStudio-SDK/AGENTS.md` for Rust-runtime constraints.

## Architecture

A Unity integration for SpriteStudio, built for performance. A thin C# "Body" drives the Rust "Brain"
(`libssruntime`) over zero-cost FFI generated by csbindgen. Per-frame geometry is built with Burst jobs and
uploaded to a `Mesh` via `SetVertexBufferData` (zero-allocation). `.sspj` projects are converted to FlatBuffers
(`.ssab`) at import time by `libssconverter`, invoked from a Unity `ScriptedImporter`.

## Key components

| Path | Role |
|---|---|
| `package/Runtime/` | Player components (`SpriteStudioPlayer` world / `SpriteStudioGraphic` uGUI), shared `SpriteStudioPlaybackCore`, and `SpriteStudioInternalPlayer` (native lifecycle / FFI / `IDisposable`). Per-frame geometry is delegated to `SpriteStudioGeometryBuilder` + the Burst `SpriteStudioMeshJob`, which in turn use focused collaborators: `SpriteStudioMeshUploader` (mesh upload / topology cache), `SpriteStudioEffectPlanBuffer` (effect draw-plan), `SpriteStudioMaskPlanner` (stencil-mask writers), `SpriteStudioNativeBuffers` (shared NativeArrays). Also `SpriteStudioNativeContext` (native-pointer ownership), `SpriteStudioUpdateManager`, Timeline, events, and the FFI bindings. |
| `package/Runtime/Plugins/`, `package/Editor/Plugins/` | Native `libssruntime` / `libssconverter` per platform — downloaded at setup, gitignored. |
| `package/Editor/` | Importers (`SpriteStudioSsabImporter`, `SpriteStudioSsqbImporter`), the conversion driver, the Importer window, and inspectors. |
| `package/Tests/` | PlayMode (Runtime) and EditMode tests. |
| `SpriteStudio-SDK/` | Rust runtime / converter submodule. |
| `scripts/` | Build & setup wrappers (`build-runtime`, `download-sdk`, `download-flatbuffers`, `run-tests`), the example-project filler (`deploy-examples`) and the release (`build-release`, which packs via `pack-release`; `release-version`). |

## Hard constraints

*   **FFI safety:** native handles (`SsPlayerHandle`) are `IDisposable`; always call `JobHandle.Complete()` before freeing native resources, or a running Burst job segfaults.
*   **Zero allocation:** the Tick / mesh-update loop must not allocate GC memory. Reuse `NativeArray`; update meshes via `SetVertexBufferData`.
*   **Canvas rebuild bypass:** `SpriteStudioGraphic` (uGUI) overrides `OnPopulateMesh` and the vertex/material dirty flags so Unity does not destroy and reallocate canvas meshes.
*   **Geometry-builder separation:** `SpriteStudioInternalPlayer` owns the native lifecycle, FFI calls, and `IDisposable`; all per-frame geometry (frame-data decode, effect/instance/mask batching, Burst scheduling, mesh upload) lives in `SpriteStudioGeometryBuilder`, its collaborators, and `SpriteStudioMeshJob`. Add rendering features there rather than in the player, and preserve the struct layouts required for Burst and FFI.
*   **Update-loop consistency:** components are batch-updated by `SpriteStudioUpdateManager`. Iterate the snapshotted `_tickCount`, not the live list, so dynamic instantiate/destroy cannot cause a `NullReferenceException`.
*   **Testing:** when changing core logic or the geometry builder, keep the tests in `package/Tests/` green.

## Documentation site

Built with [Zensical](https://zensical.org), the successor to MkDocs + Material for MkDocs. Zensical has no multi-locale build, so **each locale is built from its own config**: `mkdocs.yml` builds `docs/en` to `site/`, `mkdocs.ja.yml` builds `docs/ja` to `site/ja/`, and both inherit the shared settings from `mkdocs.base.yml`. Every page still exists as both `docs/en/<path>` and `docs/ja/<path>`; there is no fallback locale any more, so a page missing from one side is a nav entry pointing at nothing. Each locale also owns its `assets/` — a shared `docs/assets/` would sit outside both `docs_dir`s and never be copied.

**The three-config split has one rule: a YAML sequence must be defined in exactly one of the three files.** Zensical's `INHERIT` *concatenates* parent and child sequences where MkDocs replaces them — put `nav` in the base as well as a locale config and the Japanese site renders the English navigation followed by the Japanese one. Shared sequences (`theme.palette`, `theme.features`, `plugins`, `markdown_extensions`, `extra.alternate`, `extra_css`) live in `mkdocs.base.yml` and nowhere else; `nav` and `extra.social` live in the locale configs and never in the base.

Things that do **not** follow the "everything twice" rule, or that changed with the migration — check before duplicating:

*   **`overrides/main.html`** (`theme.custom_dir`) emits the Open Graph / Twitter Card tags the theme omits, **and repairs the page title**: Zensical never sets `page.is_homepage`, which its own `base.html` branches on, so the landing page would title itself "SpriteStudioPlayer for Unity - SpriteStudioPlayer for Unity". The override derives the flag from `page.url` and overrides the `htmltitle` block. **One template serves both locales** — everything is read from whichever locale config is building. Localize by adding a per-locale config override, never by branching in the template. Keep the file in sync with the copies in SpriteStudio-Docs and the sibling player repos.
*   **`overrides/partials/alternate.html`** rebuilds the header language selector so switching language keeps you on the same page. `mkdocs-static-i18n` used to rewrite those links per page; nothing does once the locales are separate builds, and the stock partial would send every reader to the other locale's home page. Driven by `extra.alternate[].link` (a locale subpath, not a URL) plus `extra.site_root_prefix` in each locale config. Known gap: the `<link rel="alternate" hreflang>` tags in `<head>` still point at each locale root — they sit inside the theme's `site_meta` block, and overriding that would mean copying thirty lines Zensical may change.
*   **`site_url` is per locale** and the ja one keeps its `ja/` suffix — `page.canonical_url`, and therefore `og:url`, is built from it.
*   **Asset paths are source-relative** (`../assets/…` from a page one level deep), including inside raw `<video>` / `<img>` HTML. Zensical resolves raw HTML `src` the same way it resolves Markdown links; MkDocs passed it through untouched. That difference is the one place where a MkDocs fallback build produces wrong output.
*   **Footer social icons are defined twice** — in `mkdocs.yml` and `mkdocs.ja.yml` (translated labels, same icons and links). Add or reorder an icon in both, or the two footers diverge. Keep `twitter:site` in `overrides/main.html` in sync with the X link.
*   **There is deliberately no `edit_uri`**, so no "edit this page" button renders. It used to point at `main` while the default branch is `develop`; nothing validates the value, and the footer repo link already routes corrections. Do not reintroduce it without checking the branch.

`mkdocs.base.yml` sets `strict: true`, so a plain `build` fails on a broken link. `serve` validates nothing — `zensical serve --strict` is accepted and currently does nothing. Nothing builds the docs on a pull request either — `pages.yml` runs on `release: published` and dispatch — so the local build is the only gate, and **both locales have to be built**, English first because it clears `site/`, which contains `site/ja`. Building only English is the easy mistake: it leaves a stale `site/ja` behind, so a Japanese page you just broke still looks fine.

`./scripts/build-docs.sh` does exactly that; `./scripts/prepare-docs.sh` sets the venv up first. Both take `key=value` options and `--help` like the other scripts here (`build-docs.sh locale=ja`, `prepare-docs.sh force=yes`), both have `.ps1` twins, and they wrap nothing more than `pip install -r docs/requirements.txt` and the two `zensical build` runs. Every repository in the family spells this pair the same way, and the `-docs` suffix keeps it apart from the scripts that build the code.

`./scripts/build-pages.sh` is the published site: that pair, run for you, plus a static server over the result (`serve=yes` — the only way to see both locales at once and the language selector resolving between them, since `zensical serve` builds one locale at a time). The site here carries nothing but the docs, so it adds no build step of its own. `pages.yml`'s build job **is** this script (`prepare=no serve=no`, every option spelled out so a publish cannot change because a default did), so CI and the local gate cannot drift, and `build-pages.sh` means the same thing in every repository in the family — including the ones whose site carries a demo or an API reference as well.

Two things to know about callouts, which Zensical parses natively now that `mkdocs-callouts` is gone: a list inside a `> [!NOTE]` block needs a blank `>` line before it or it renders as literal text, and `[!IMPORTANT]` is not a built-in admonition type — `docs/*/stylesheets/extra.css` styles it to keep the appearance it had. Also **avoid `src="…"` / `href="…"` inside an inline code span**: Zensical rewrites paths there as if they were real links, corrupting the example. Use a fenced block, which it leaves alone.

## Releases

A release is a tag, pushed first and built second:

```bash
git tag v7.0.0-beta.1 && git push origin v7.0.0-beta.1
# Actions → Release → "Use workflow from" = v7.0.0-beta.1, upload_release = true
# → a draft Release on that tag → review the assets → Publish from the UI
```

Nothing passes the tag around: `build-release.sh` reads `GITHUB_REF_NAME` (or, locally, the tag `HEAD` is checked out at), and `release.yml` uses the same ref for `tag_name`. Dispatching from a branch is a package build, not a release — `upload_release=true` from anything but a `v*` tag fails the run rather than silently skipping the Release. `scripts/release-version.sh` prints what the tag *should* be (`version` in `package/package.json`, **not** `SDK_VERSION.txt`), and `build-release.sh` says so when the two disagree.

Publishing the draft is what emits the `release: published` event that triggers the Pages deploy, and what makes `releases/latest/download/<name>.tgz` — the install URL in the README and the docs — resolve. Keep it a full, non-prerelease release, and publish it by hand.

`scripts/build-release.sh` is the release, and `release.yml`'s job **is** this script (`sdk=download out=release-dist verify=yes clean=yes`, every option spelled out so a release cannot change because a default did), so CI and a local run cannot drift. Unlike the SDK's script of the same name, this one really does produce the whole thing on one machine — the package is C# plus prebuilt native libraries — so the way to review a release is to build it and install the tarball:

```bash
./scripts/build-release.sh
# Window > Package Manager > + > Install package from tarball...
```

It checks twice, for different failures. **Before packing:** every plugin directory has native libraries, each has a committed `.meta`, and both FFI bindings and their `.meta` are there. A UPM package is extracted into an immutable folder, so Unity ignores any asset with no `.meta` — a lib whose `.meta` was never committed installs as *nothing*, silently, and CI has no Unity to generate one. **After packing:** the tarball actually contains them. `npm pack` applies the `files` allowlist in `package.json`, a second place a file can vanish that the first check cannot see. (`LICENSE.md` is deliberately absent from `files` — npm always includes a `LICENSE*`, so only its `.meta` has to be listed. The check asserts it rather than trusting anyone to remember.)

`sdk=<download|build>` says where the native libraries come from — the same pair every `build-pages.sh` in the family uses. `download` is `download-sdk.sh`: the pre-built release for `scripts/SDK_VERSION.txt`, every platform, and so the only source a shippable package can have. `build` is `build-runtime.sh`, compiled from the Rust source in the submodule, and it is what to use while the SDK release that version file names does not exist yet — at the cost of **only this host's platform**.

The checks cannot tell those apart: they ask that each plugin tree has libraries, not that it has all of them, so a one-platform tarball passes. The script says so out loud instead. Use `sdk=build` to get a package to look at; never to cut a release.

```bash
./scripts/build-release.sh sdk=build   # a package, this host only
```
