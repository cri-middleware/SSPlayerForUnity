# Build Guide (for Developers)

[← Back to documentation index](../index.md)

For normal use, the package already includes prebuilt native libraries, so the steps on this page are not required. They are only needed when **developing the plugin itself** or when **rebuilding the native libraries for a specific platform**.

The build compiles the Rust-based SDK (`libssruntime` / `libssconverter`) and places it into the `Plugins` folder on the Unity package side. At the same time, the C# FFI bindings generated by `csbindgen` are also copied.

## Prerequisites

The build requires the **Rust toolchain (`cargo`)**. If it is not installed, install it from [rustup](https://rustup.rs/).

If you cross-compile (build for a different platform), you also need the SDK / toolchain for the target platform (Android NDK, Emscripten, Xcode, etc.).

## Steps

1. Fetch the repository including submodules to prepare `SpriteStudio-SDK`.

   ```sh
   # For a fresh clone
   git clone --recursive https://github.com/cri-middleware/SSPlayerForUnity.git

   # If you have already cloned
   git submodule update --init --recursive
   ```

2. Run the build script.

   ```sh
   # macOS / Linux
   ./scripts/build-runtime.sh

   # Windows (PowerShell)
   .\scripts\build-runtime.ps1
   ```

3. `libssruntime` and `libssconverter` are compiled and automatically placed in the following locations.

   - `package/Runtime/Plugins/<Platform>/<Arch>/` — `libssruntime` (used at runtime)
   - `package/Editor/Plugins/<Platform>/<Arch>/` — `libssconverter` (used for conversion in the editor)
   - `package/Runtime/Bindings/SSRuntimeMethods.g.cs` — generated FFI bindings
   - `package/Editor/Bindings/SSConverterMethods.g.cs` — same as above (for conversion)

## Build Options

By passing arguments, you can switch the target platform, architecture, and build mode (if not specified, a debug build for the host environment is produced).

```sh
./scripts/build-runtime.sh platform=<platform> arch=<arch> build=<mode>
```

| Option | Value | Description |
|---|---|---|
| `platform` | `windows` / `macos` / `linux` / `android` / `ios` / `web` | Target platform |
| `arch` | `x86_64` / `arm64` / `universal`, etc. | Target architecture |
| `build` | `debug` / `release` | Build mode (`release` for distribution) |

Examples:

```sh
# Release build for Windows x86_64
.\scripts\build-runtime.ps1 platform=windows arch=x86_64 build=release

# Release build for Android arm64
./scripts/build-runtime.sh platform=android arch=arm64 build=release

# iOS (generates an XCFramework containing both device and simulator)
./scripts/build-runtime.sh platform=ios build=release
```

> **About iOS:** `platform=ios` generates a `libssruntime.xcframework` containing both the device (arm64) and simulator (arm64 / x86_64) slices, and places it in `package/Runtime/Plugins/iOS/`. Since device / simulator are separated within the XCFramework, no simulator-only option is needed (it also works on the simulator on Apple Silicon Macs).

> **Note:** If you specify the same platform/arch as the host environment, `cargo build` is run directly. Otherwise (cross-compilation), the work is delegated to the release script on the SDK side.

## Regenerating Only the FFI Bindings

When FFI is added or changed on the SDK side and you want to regenerate only the binding code, run the following.

```sh
# macOS / Linux
./scripts/generate-runtime-code.sh

# Windows (PowerShell)
.\scripts\generate-runtime-code.ps1
```

> Do not manually edit the generated files (`SSRuntimeMethods.g.cs`, `ssab_generated.cs`, etc.). Always regenerate them with the script.

## Common Pitfalls

- **Unity keeps holding an old native DLL**: On Windows, the editor may keep holding a native DLL that was loaded at startup. If replacing the build does not take effect, **quit the Unity editor, build, and then restart it**.
